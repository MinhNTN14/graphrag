GraphRAG,
end to end.

A hybrid retrieval system: a Neo4j knowledge graph and a vector index, built from your documents and queried together — visualized stage by stage, with the reasoning you'd give out loud.

Neo4j 5 · vectors + graph Google Gemini FastAPI Streamlit
The one idea. Each document is split into chunks; every chunk becomes a 768-dim embedding vector and is passed to an LLM that extracts entities & relationships. Both land in Neo4j, stitched together by a MENTIONS edge. At query time we retrieve two ways — vector similarity and graph traversal — merge them, and let Gemini answer from that grounded context.

Why the graph? Plain vector RAG answers "what does the doc say about X?" but stumbles on "how are A and B related?" — multi-hop questions whose answer lives in the connections between facts, not in any single passage. The graph stores those connections explicitly.

Chunking that keeps meaning

Semantic, structure-aware chunking

Fixed-width word windows slice through the middle of sentences and glue unrelated content together. Instead, the chunker parses the document into blocks — headings, paragraphs, tables, images, code — and packs prose by whole sentences, so a chunk never ends mid-thought.

Say it out loud

Interview questions

QWhat is GraphRAG, and how is it different from normal RAG?

Normal RAG embeds the query, pulls the top-k similar chunks, and stuffs them in the prompt. GraphRAG adds a knowledge-graph layer: during ingestion an LLM extracts entities and relationships, and at query time we also retrieve by traversing that graph. The payoff is multi-hop reasoning — answers that depend on how facts connect, not on one passage. Hybrid mode combines both signals.

QWhy store embeddings in Neo4j instead of a dedicated vector DB?

The whole value is joining semantic similarity with graph structure. If vectors live in Pinecone and the graph in Neo4j, every hybrid query is a cross-system join you orchestrate yourself. In one store, a chunk's vector and its MENTIONS/RELATES_TO edges are one MATCH apart. The trade-off: a specialised vector DB scales to far more vectors — at billions I'd reconsider.

QWalk me through a hybrid query.

Embed the question; vector-search the index for top-k chunks by cosine. Extract entities from the question; match them, traverse ≤2 RELATES_TO hops, and collect chunks that mention any reached entity. Merge and dedupe by chunk_id — chunks found by both paths are the strongest signal. Build a context + relationships block and prompt Gemini to answer only from it, with citations.

QHow does the chunker preserve meaning?

It's structure-aware: text is parsed into heading / paragraph / table / image / code blocks. Tables, images and code stay atomic (each its own chunk); prose is packed by whole sentences so a chunk never ends mid-sentence; overlap carries whole trailing sentences. Each chunk records its section heading, prepended for topic context. That beats blind fixed-width windows, which cut through sentences.

QHow do you handle model retirement and rate limits?

Model ids get retired, so at start-up the app calls list_models() and picks the newest available from a priority list, with a static fallback — it self-heals instead of 404-ing. Free-tier rate limits are ridden out with tenacity exponential backoff, and reduced by using bigger chunks; a chunk write is idempotent (MERGE), so an interrupted ingest just resumes.

QHow do you prevent hallucination?

Grounding: the prompt says answer only from the provided context, admit when it's insufficient, and cite the chunk/doc. Retrieval quality is the real lever — good chunks in, faithful answer out — and returning sources lets a user verify every claim.
